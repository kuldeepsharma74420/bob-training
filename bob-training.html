Ignoring Files — .bobignore
⏱ 20 min
What is .bobignore?

Control which files BOB can access by creating a .bobignore file in your project root. It works just like .gitignore — list patterns to define BOB's operational scope.

🎯 Purpose
  • Protect sensitive information
  • Prevent accidental changes to build artifacts
  • Exclude large assets from BOB's context
  • Define BOB's operational scope in your workspace
ℹ️ BOB actively monitors the file — any changes reload automatically. The .bobignore file itself is always implicitly ignored so BOB cannot change its own access rules.
Pattern Syntax (same as .gitignore)
PatternDescription
node_modules/Ignores entire node_modules directory
*.logIgnores all files ending in .log
config/secrets.jsonIgnores a specific file
!important.logException — BOB will NOT ignore this file even if *.log exists
build/Ignores the build directory
docs/**/*.mdIgnores all Markdown files in docs/ and subdirectories
✅ Create the file at your workspace root: .bobignore — no additional configuration needed.

How BOB Tools Interact with .bobignore
⏱ 20 min
✅ Strict Enforcement (Reads & Writes)

These tools directly check .bobignore before any file operation. If a file is ignored, the operation is blocked:

ToolBehaviour
read_fileWill not read ignored files
write_fileWill not write to or create ignored files
apply_diffWill not apply diffs to ignored files
GetSymbolsOverviewWill not parse ignored files for code symbols
🔍 File Discovery & Listing
  • 1
    list_files — ignored files are omitted or marked with 🔒
  • 2
    Workspace environment details (open tabs, project structure) are filtered to exclude ignored items
⚠️ File Editing Tools (Potential Write Bypass)
⚠️ insert_content and search_and_replace — the final write operation may bypass .bobignore rules. Initial reads are blocked, but the save action does not have an explicit check.
🖥️ Command Execution

The execute_command tool checks if a command (from a predefined list like cat or grep) targets an ignored file — if so, the command is blocked.

🔔 User Notifications
  • 1
    � Visual cue — ignored files marked with a lock symbol in file listings
  • 2
    Error message — "Access to [file_path] is blocked by the .bobignore file settings"
  • 3
    Chat notification — visible alert when an action is blocked

Key Limitations & Scope
⏱ 20 min
Known Limitations
⚠️ Workspace-Centric Only

Rules apply only to files within the current BOB workspace root. Files outside this scope are not affected.

⚠️ execute_command Specificity

Protection is limited to a predefined list of file-reading commands (e.g. cat, grep). Custom scripts or uncommon utilities may not be caught.

⚠️ insert_content & search_and_replace

These tools may write to ignored files due to current limitations in their save mechanism — the write step does not check .bobignore.

⚠️ Not a Full Sandbox

.bobignore is powerful for controlling file access via BOB's tools, but it does not create a system-level sandbox.

Quick Reference Summary
AspectDetail

SyntaxIdentical to .gitignore
Auto-reload✅ Yes — changes take effect immediately
Self-protection✅ BOB cannot edit its own ignore rules

✅ Best practice: always add *.env, secrets/, credentials*, and node_modules/ to your .bobignore from day one.

Subagents — What They Are & How They Work
⏱ 20 min
What is a Subagent?

A subagent is an independent agent BOB can spawn to handle a focused, self-contained task. It runs in its own isolated context window, executes its work, and returns a summary back to the main conversation — without polluting it.

How Subagents Work
  1. 1
    A new independent agent is created with its own context window
  2. 2
    BOB passes it a description of the focused task
  3. 3
    You are prompted to approve the spawn before it starts
  4. 4
    The subagent executes the task using its available tools
  5. 5
    It returns a summary of findings back to BOB
  6. 6
    BOB uses that summary to continue the main conversation
ℹ️ The subagent does not share state, files, or tool results with BOB unless BOB explicitly passes them in the description.
Subagent Types
TypeDescriptionBest For
exploreRead-only, lighter modelSearching code, finding files, understanding structure
generalFull tool access, default modelAny self-contained task — reads, writes, commands
When BOB Uses Subagents

BOB uses subagents sparingly. All of these must be true:

  • ✓
    The task is clearly self-contained and only a summary is needed back
  • ✓
    It would add significant irrelevant content to the main context
  • ✓
    Cannot be done with one or two direct tool calls
⚠️ BOB does not use subagents for simple file reads, quick searches, single-tool operations, or when context is already available.

Subagents vs Subtasks & Context Rules
⏱ 20 min
Subagents vs Subtasks
SubagentSubtask
VisibilityRuns silently in backgroundAppears in UI with breadcrumb & conversation
InteractionNot interactive — returns only a summaryFully interactive — follow progress & continue
PurposeGather info without polluting main contextComplex work needing tracking & dedicated thread
OutputSummary returned to BOBIndependent conversation thread
✅ Use subagents for background information-gathering. Use subtasks for complex work that benefits from visibility and a dedicated conversation.
Context & Conversation History
📋 Default — No Parent History

By default a subagent does not see the parent conversation. This keeps its context lean and focused on the task.

🔀 fork_context: true

When a subagent needs to understand prior decisions or constraints, BOB sets fork_context: true to pass the conversation history into the subagent.

Mode Restrictions

The active mode controls which subagent types BOB is permitted to spawn. Some modes allow all types; others restrict or disallow spawning entirely.

ℹ️ If a subagent spawn is not permitted by the active mode, BOB completes the work directly without spawning.

What is Bobalytics?

Bobalytics provides analytics and insights into how IBM BOB contributes to your software development process — tracking codebase impact, Bobcoin spending, and team adoption.

⚠️ Bobalytics is available exclusively for Enterprise plan users. Access it via bob.ibm.com → Admin → Bobalytics.
Analytics Views
ViewWho Can See ItShows
🏢 WorkspaceAdmins onlyAggregated data across all teams — org-wide adoption, value, cost
👥 TeamAdmins (all charts) + Users (anonymized)Analytics for a specific team — user emails shown as User 1, User 2…
👤 UserEvery user (own data only)Personal analytics — admins cannot view other users' data
Three Key KPIs
📈 Adoption Rate

Avg daily active users ÷ total licensed seats. A user is active when they accept a code completion or complete a chat conversation.

⚡ Bob Factor

Lines of code committed by BOB ÷ total lines committed. Measures BOB's tangible contribution to shipped code.

💰 Bobcoin Spend

Total Bobcoins consumed over the selected period. Track daily spend and compare team-level cost vs. impact.

Skills — What They Are & Why Use Them
⏱ 20 min
What Are Skills?

Skills are reusable instruction sets that teach BOB new workflows and specialised tasks. Think of them as recipes that BOB follows to complete specific types of work in a consistent, repeatable manner.

How Skills Work
  1. 1
    You activate a skill (or BOB auto-activates based on your request)
  2. 2
    BOB receives the skill's instructions + access to supporting files
  3. 3
    BOB follows the defined workflow to complete your task
ℹ️ Skills load once per conversation. BOB automatically determines when to activate a skill based on your request and the skill's description.
Why Use Skills?
♻️ Reusability

Define workflows once and use them across multiple conversations

🎯 Consistency

Ensure BOB follows the same approach every time for specific tasks

🧠 Specialisation

Create domain-specific expertise for code reviews, testing, documentation, and more

👥 Team Collaboration

Share standardised workflows across your team through version control

🗂️ Flexibility

Include supporting files like checklists, templates, and reference materials
